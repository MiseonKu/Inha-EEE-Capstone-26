# P1 ML Architecture Notes Without IMU

For the current P1 phase, the available real-robot signals are:

- encoder angles from the robot,
- Vive Tracker position,
- fixed target/reference coordinates generated by this project.

The RViz/URDF coordinate is the rigid target/reference. It is not the label.

## Recommended First Architecture

Use the model as an actual-position or actual-error predictor:

```text
input X:
  q_encoder_settled
  q_cmd_target
  p_target_base
  p_fk_base = FK(q_encoder_settled)
  optional trajectory features

label Y option A:
  p_vive_settled_base

label Y option B:
  delta_p = p_vive_settled_base - p_fk_base
```

Option B is often cleaner because the network learns the flexible-link residual
relative to the rigid model instead of relearning rigid FK.

## Runtime Compensation

Given a fixed desired target `p_target_base`:

1. Compute a nominal rigid command angle.
2. Generate nearby candidate angles.
3. For each candidate, use ML to predict `p_vive_pred_base`.
4. Choose the candidate minimizing:

```text
||p_vive_pred_base - p_target_base||
```

This matches architecture candidate 1 in the Word document:

```text
ML actual position prediction + optimization/search
```

## Why Not Direct New-Angle Output First

Directly predicting `q_new` requires a reliable `q_new` label. That means the
real robot must already be manually/automatically adjusted until the Vive
Tracker reaches the target, then the resulting angle becomes the label. This is
much slower and can be ambiguous when multiple angles can reach similar
positions.

For P1, collect actual-position labels first:

```text
target_id, p_target_base, q_cmd, q_encoder_settled, p_vive_settled_base
```

Then build compensation by optimization around the learned actual-position
model.
